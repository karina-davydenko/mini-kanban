# Мини-канбан

Приложение для работы с задачами на React, TypeScript, Material UI, NestJS и PostgreSQL. В нём реализованы создание, просмотр, редактирование и удаление задач, а также перемещение между колонками «Новая», «В работе» и «Готово». Данные сохраняются через REST API в PostgreSQL и остаются после перезагрузки страницы.

Актуальная версия решения находится в ветке `main`. История разработки сохранена в `feature/mini-kanban`.

## Запуск

Требуются Node.js 22.23.3, npm и Docker с Docker Compose. При использовании `nvm` версия Node берётся из `.nvmrc`.

```sh
git clone https://github.com/karina-davydenko/mini-kanban.git
cd mini-kanban
nvm install
nvm use
npm ci
cp .env.example .env
cp backend/.env.example backend/.env
cp frontend/.env.example frontend/.env
docker compose up -d db
docker compose ps
```

Перед применением миграции сервис `db` должен иметь состояние `healthy` в выводе `docker compose ps`.

```sh
npm run db:migrate
npm run db:generate
```

Backend и frontend запускаются в двух отдельных терминалах из корня проекта:

```sh
npm run dev:backend
```

```sh
npm run dev:frontend
```

Интерфейс: `http://localhost:5173`. API: `http://localhost:3000/tasks`. PostgreSQL использует порт `5432`. В корневом `.env` задаются параметры контейнера; `backend/.env` содержит `DATABASE_URL`, порт API и разрешённый адрес frontend (`FRONTEND_ORIGIN`); `frontend/.env` содержит адрес API (`VITE_API_URL`). При изменении параметров базы `DATABASE_URL` должен им соответствовать. Примеры переменных находятся в `.env.example`; локальные `.env` исключены из Git.

## Устройство приложения

Frontend отправляет запросы к API NestJS. Backend валидирует данные и работает с PostgreSQL через Prisma. Схема находится в `backend/prisma/schema.prisma`, миграция — в `backend/prisma/migrations`. Для задач доступны `GET /tasks`, `GET /tasks/:id`, `POST /tasks`, `PATCH /tasks/:id` и `DELETE /tasks/:id`.

Название обязательно и не может состоять только из пробелов. Описание необязательно. Максимальная длина названия — 160 символов, описания — 4000. Статус новой задачи — `new`, приоритет по умолчанию — `medium`; эти значения заданы в схеме базы. Сервер проверяет ID, допустимые статусы и приоритеты, а также поля запроса. Пустой `PATCH` и неизвестные поля дают `400`, отсутствующая задача — `404`.

В интерфейсе есть состояния загрузки, ошибки с повторной попыткой и пустой доски. Смена колонки выполняется выбором статуса в карточке. После успешного изменения доска показывает ответ API. На узком экране колонки располагаются вертикально.

## Проверки

```sh
npm test --workspace backend
npm run build
```

Шесть backend-тестов проверяют валидацию, отсутствие явной передачи значений, заданных по умолчанию в БД, смену статуса, ответы `404` и отклонение пустого обновления. В них используется подмена слоя хранения; реальную запись в PostgreSQL эти тесты не проверяют. Отдельно на временной чистой базе были выполнены миграция и CRUD-запросы к работающему API. Временная база после проверки удалена, рабочие данные не затронуты. Установка через `npm ci`, backend-тесты и сборки обоих приложений прошли на Node.js 22.23.3. Ручная проверка подтвердила создание задачи, сохранение после перезагрузки, просмотр, редактирование, смену статусов, удаление и отображение на телефоне. Также проверены ошибка загрузки с повторной попыткой и ошибка создания без потери введённого текста.

## Ограничения и развитие

- Авторизации нет: доска общая для всех пользователей. Приложение рассчитано на локальный запуск и не подготовлено для production.
- Перетаскивание и ручная сортировка внутри колонки не реализованы. Задачи выводятся по времени создания от новых к старым, при совпадении времени — по ID.
- Небольшое возможное улучшение — фильтр задач по приоритету. Сейчас он не реализован.

Зафиксированный интервал работы — примерно с 09:50 до 13:00 20 октября 2026 года, около 3 ч 10 мин вместе с паузами и финальной проверкой. Точное начало подготовительных действий до 09:50 отдельно не фиксировалось, поэтому полное время могло быть больше.

## Использование AI

AI применялся для обсуждения структуры, конфигурации, генерации и доработки кода, тестов, ревью и документации. Результат проверялся сборками, автоматическими тестами, запросами к реальному API и PostgreSQL, а также ручными сценариями в интерфейсе, перечисленными выше.
